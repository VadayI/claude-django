## Мета

Зробити план **живим артефактом**: оркестратор заводить `docs/plans/NNNN-<slug>.md` на старті non-trivial задачі, а агенти **ведуть його у процесі** — фіксують підтвердження виконання та зміни курсу, не переписуючи заднім числом. Сьогодні плани створюються в Plan Mode й після затвердження «застигають»: фактичний хід роботи в них не повертається, тож вони дрейфують від реальності та дублюються з WORKLOG. «Живий план» закриває цей розрив, лишаючись у межах філософії проєкту (Simplicity First — без нових інструментів, лише дисципліна + один шаблон + одне правило).

## Модель документа (що саме «живе»)

Кожен `docs/plans/NNNN-*.md` отримує три керовані секції поверх звичайного тіла плану:

1. **Status-таблиця** (вгорі) — крок / стан (`pending`/`in_progress`/`done`/`blocked`) / власник-агент. Оновлюється по ходу; це «курсор» плану.
2. **Execution log** (append-only) — короткі підтвердження фактів виконання: «крок N зелений (pytest)», «контракт зафіксовано в endpoints.json», «gate: 1×🟡 → повернуто django-developer». Дописується, ніколи не редагується заднім числом.
3. **Amendments** (append-only) — зміни курсу: якщо рішення плану змінилось, оригінальний абзац **не видаляється**; натомість додається запис у Amendments + інлайн-вказівник біля оригіналу (`> ⚠️ Змінено — див. Amendment #k`). Історія рішень лишається прозорою.

## Затверджені рішення (3 відкриті питання — закриті 2026-06-05)

1. **Скоуп ведення плану = кожна non-trivial задача.** Той самий поріг, що активує Plan Mode (`@.claude/rules/workflow.md`): 3+ кроки, архітектурне рішення, або >2 файлів. Тривіальні задачі (типо, один конфіг-рядок) плану не заводять.
2. **Gate-агенти не пишуть у план напряму.** `reviewer` / `security-scanner` / `dba` у Quality Gate лишаються read-only (вони не редагують ні код, ні план): вони **репортують оркестратору**, а оркестратор вносить запис у Execution log. Зберігає інваріант «gate-агенти лише читають і звітують».
3. **Нумерація `NNNN` — оркестратор при сідінгу.** Номер присвоює оркестратор у момент заведення файлу плану (наступний вільний у `docs/plans/`), а не агенти. Уникає гонок за номер між паралельними агентами.

Додатково: **Execution log ≠ WORKLOG.** Execution log — внутрішньоплановий журнал підтверджень під час виконання однієї задачі. `docs/WORKLOG.md` — міжсесійна хроніка, єдиний власник — `/wrap-up`. Вони не дублюються: план фіксує хід конкретної задачі, WORKLOG — підсумок сесії.

## Спосіб виконання (важливо для цього mount)

- Усі правки — через **bash heredoc → scratch (`/dev/shm`) → `cp` → `cmp`/`wc -c`/no-NUL**. MCP Edit/Write на /mnt обрізають хвіст (або пишуть NUL) — не використовувати. Scratch-каталог не переживає окремий bash-виклик → write+cp+перевірка в **одному** виклику.
- `git add/commit/push` — з **host-шела**, не з sandbox (9p ламає index/config). Template-repo дозволяє прямий push у `main`; групувати по логічних комітах.
- Жодних записів у `.git/**` з /mnt-боку.
