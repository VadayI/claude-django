# Аудит якості шаблону claude-django

**Дата:** 2026-06-01
**Тестовий проєкт:** `example-service`
**Сценарій:** clone → `/doctor` → `/bootstrap` → `Project_Data` + `/synthesize-brief` → `/preflight` → фіча «імпорт продуктів» → `/wrap-up`
**Метод:** два незалежні проходи — оглядовий + скептичний (з реальним запуском `manage.py check`, drift-gate, ruff, Python-репро).

---

## Підсумкова оцінка

Шаблон **працює і дає сильний каркас**: повний скафолд, бездоганний TDD-порядок (тести закомічені до коду), Conventional Commits, OpenAPI-схема реально синхронна з кодом (drift-gate проходить), ruff чистий, докстрінги на місці. Це далеко вище за «AI-згенерований код навмання».

Але **це не «exemplary»**. Є три серйозні проблеми процесу/шаблону і дві небезпечні логічні діри в згенерованій фічі. Найважливіше: **результат роботи фактично не доставлений** — фіча застрягла на гілці, а `/wrap-up` залишив проєкт у неузгодженому стані й збрехав про статус у документації.

---

## A. Дефекти процесу та шаблону (головне для claude-django)

### 🔴 1. `/wrap-up` не завершує роботу і вводить в оману
- PR #4 (`feat/product-import`) **не змержено**. `origin/main` містить лише 4 коміти (bootstrap → lint → brief → ADR); жодного коміту фічі. Уся продуктова логіка живе тільки на гілці (`git rev-list --count origin/main..feat/product-import` = 6).
- `HANDOFF.md` — **100% плейсхолдерів `{TODO}`** у кожній секції. Файл сам інструктує заповнювати його через `/wrap-up`; цього не сталося.
- Робоче дерево **брудне після wrap-up**: незакомічені `.gitignore` (саме фікс артефактів build/) і `docs/WORKLOG.md`.
- `WORKLOG.md` стверджує, що `main = PR#1+#2+#3`, хоча merge-історії немає (коміти лінійні, прямі), а фічу подає як «готову до merge» — тобто доставленою вона не є.

**Висновок для шаблону:** команда `/wrap-up` повинна (а) заповнювати `HANDOFF.md` з реального git-стану, (б) комітити власні правки WORKLOG, (в) **верифікувати** твердження про merge через `gh pr view`/`git branch --merged`, а не записувати наміри як факт. Зараз вона генерує документацію, яка суперечить дійсності — це найгірший клас помилки для «контексту в git».

### 🟡 2. Дефект скафолда: `pyproject.toml` без `setuptools.packages.find`
Коміт `75e5add fix: configure setuptools package discovery` латає баг **самого шаблону**: згенерований `backend/pyproject.toml` не має `[tool.setuptools.packages.find]`, тож при двох top-level пакетах (`apps/`, `config/`) flat-layout автодискавері падає з «multiple top-level packages discovered», і `pip install -e`/CI install ламається. **Кожен проєкт зі шаблону впреться в це.** Фікс (`include = ["apps*","config*"]`) треба внести в `templates/pyproject.toml`.

### 🟡 3. README застряг у RED-фазі; джерела суперечать одне одному
`backend/apps/products/README.md` після релізу досі каже *«Status: scaffolding (TDD RED phase)… target surface»*. Правило `app-readme.md` вимагає оновлювати README у тому ж PR, що й код — не виконано. Плюс `sub-brands` існує/не існує по-різному в README / `INDEX.md` / `WORKLOG` / коді (`_SLUG_TO_TYPE`). `docs/STUBS.md` теж лишився незайманим шаблоном.

### 🟢 4. Дрібниці середовища
Порожній `.git/index.lock` (класичний `/mnt`-артефакт) — нешкідливо, але варто, щоб хуки/команди чистили його.

## B. Дефекти згенерованої фічі (якість агентів)

### 🔴 1. `except Exception` per-row → корупція виглядає як успіх
`services.py:239,327` обгортають кожен рядок у `except Exception: errors.append(...); skipped += 1`. Будь-яка програмна помилка чи збій БД під час імпорту глушиться по-рядково, а ендпоінт повертає **200 «success»**. Клієнт, що дивиться лише на статус, не відрізнить чистий імпорт від зіпсованого.

### 🔴 2. `format=csv` + JSON-файл → мовчазний junk-продукт, 200
`csv.DictReader` по JSON-байтах дає рядки без потрібних ключів → `Product(source_id="", name="")` створюється і повертається `created:1`. Немає валідації заголовків CSV і обовʼязковості `name`. Тест на mismatch покриває лише зворотний напрямок (CSV-як-JSON).

### 🟡 3. 409 не атомарний
Перевірка `source_id` — read-then-write через `UniqueValidator`, не на рівні БД. Два конкурентні create з однаковим `source_id` → `IntegrityError` → необроблений **500**, а не 409. Немає `try/except IntegrityError` навколо `perform_create`.

### 🟡 4. Решта
Файл читається в памʼять цілком, без ліміту розміру й throttle (DoS-by-bigfile, хоч і admin-only). Приймається лише `utf-8-sig` — реальні польські `cp1250` відкидаються сирим codec-400. Тести: немає кейсів JSON-як-CSV, кодування, порожнього `name`, конкурентності; 409-тести перевіряють лише happy-path валідатора.

### ℹ️ Що реально добре (після перевірки)
Drift-gate **справді проходить** (схема синхронна). Лічильники created/updated/skipped без off-by-one. Race-retry для словникових записів **безпечний** (власний savepoint у `get_or_create`). DB-state перевіряється в тестах, тріангуляція для upsert реальна. PUT справді вимкнено, валідація — у серіалайзерах.

## C. Рекомендації для claude-django (за пріоритетом)

1. **Полагодити `/wrap-up`** — заповнення `HANDOFF.md` з git-стану, коміт власних змін, верифікація merge-статусу через `gh`. Це найважливіше: зараз команда продукує оманливий контекст.
2. **Внести фікс `setuptools.packages.find` у `templates/pyproject.toml`** — усуває гарантований баг install для кожного нового проєкту.
3. **Підсилити `reviewer`/quality-gate** евристиками на «німі провали»: широкий `except Exception`, відсутність валідації content-vs-format, незахищений `perform_create` від `IntegrityError`. Ці класи помилок пройшли крізь гейт.
4. **Зробити оновлення per-app README та ініціалізацію `docs/STUBS.md` частиною GREEN/docs-фази**, з перевіркою узгодженості ендпоінтів між README / INDEX / OpenAPI.
5. **Розширити стандартний тест-чекліст агента `tester`**: обидва напрямки format-mismatch, кодування, порожні обовʼязкові поля, конкурентний конфлікт.

**Загальний вердикт:** каркас і дисципліна шаблону — сильні (TDD, OpenAPI, commits, lint). Слабкі місця — на «останній милі»: фінальна доставка (`/wrap-up` + merge) і глибина quality-gate проти тихих логічних провалів. Виправивши пункти 1–3, шаблон вийде на справді продакшн-рівень.
