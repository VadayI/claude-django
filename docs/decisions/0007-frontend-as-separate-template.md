# 7. Фронтенд — окремий шаблон, що споживає OpenAPI-контракт

- **Status:** Accepted
- **Date:** 2026-06-01
- **Deciders:** Project maintainer
- **Tags:** architecture, frontend, templates, contract

## Контекст

Початковий blueprint середовища (`LOCAL/claude-django-react-environment.md`, 2026-05-27) передбачав **monorepo**: один репозиторій з `backend/` (Django+DRF) і `frontend/` (Vite+React) як міні-клієнт для ручного тестування API. Аргумент тоді — соло-розробка на двох машинах і бажання, щоб код + контекст Claude синхронізувалися одним `git pull`, без ризику розсинхрону.

Згодом проект свідомо еволюціонував у **backend-only**: інтерактивне тестування API перейшло на Swagger UI/Redoc (`drf-spectacular`), а реальний фронтенд винесено в окремий репозиторій (ADR `0001`, `rules/architecture.md`, `rules/api-docs.md`). `docs/api/openapi.yml` під CI drift-gate став єдиним контрактом.

Maintainer хоче, щоб проекти могли **відразу працювати в React+MUI**, коли потрібен фронтенд. Розглянуто три варіанти:

- **A. Окремий fullstack-шаблон** (`claude-django-react` = backend + `frontend/` в одному репо) — monorepo-зручність, але дублювання backend-конфігу між шаблонами.
- **B. Окремий frontend-only шаблон** (`claude-react-mui`), що споживає `openapi.yml`.
- **C. Вбудувати фронтенд у цей репо** — конфлікт з backend-only ідентичністю, frontend-баласт у кожному backend-проекті, потрібне скасування ADR `0001`/`architecture.md`.

## Рішення

Обрано **варіант B**. Цей репозиторій лишається **backend-only**. Фронтенд живе в окремому шаблоні-репозиторії **`claude-react-mui`** (Vite + React + **TypeScript** + MUI), який споживає `docs/api/openapi.yml` як контракт.

«Швом» між стеками є OpenAPI-схема:

1. **Генерація типізованого клієнта.** Frontend-шаблон генерує API-клієнт і типи зі схеми (напр. `openapi-typescript` + `openapi-fetch`, або `orval`). Ручних типів під ендпойнти не пишемо.
2. **Прив'язка до версії контракту.** Frontend фіксує версію/хеш схеми (з `info.version` або контрольної суми `openapi.yml`); CI фронтенду перегенеровує клієнт і **падає на дрейфі** — дзеркало backend-gate `scripts/check_openapi_drift.sh`.
3. **Власний фокусований `.claude/`.** У `claude-react-mui` свої агенти/скіли/правила під фронтенд (UI-компоненти, MUI-патерни, React Query/стан, Playwright e2e, accessibility), без backend-шуму. Це відповідає принципу «менше зайвого = чистіше середовище для агента».
4. **Розділення CI та релізів.** Бекенд і фронтенд мають незалежні pipeline і цикли релізів; контракт — єдина точка звʼязності.

Для fullstack-проекту створюються **два репо поряд** (backend + frontend), синхронізовані через схему. Цим скасовується monorepo-рекомендація початкового blueprint.

## Наслідки

**Плюси.** Цей шаблон зберігає чисту backend-only ідентичність і всі свої gate (OpenAPI drift, per-app README, ledger стабів). Кожен стек має сфокусований набір агентів. Типобезпека фронтенду похідна від контракту, а не дублюється вручну. Незалежні релізи.

**Мінуси.** Контекст Claude розділений між двома репо — для соло-роботи на двох машинах це реактивує занепокоєння початкового blueprint щодо розсинхрону; помʼякшується тим, що `git pull` обох репо тривіальний, а схема — детермінований контракт. Два репо на fullstack-проект (трохи більше церемонії, ніж один `git clone`).

**Відкинуті альтернативи.** Варіант C (вбудувати) — відхилено через конфлікт з backend-only архітектурою і frontend-баласт у backend-only проектах. Варіант A (fullstack-шаблон) — відхилено через дублювання backend-`.claude/` між двома шаблонами і ризик їхнього розсинхрону.

## Наступні кроки (поза цим репо)

1. Створити репозиторій-шаблон `VadayI/claude-react-mui` (Vite+React+TS+MUI), з власним `.claude/` і генерацією клієнта з `openapi.yml`.
2. Документувати handshake: який ендпойнт/файл публікує схему, як фронтенд її тягне (subtree/submodule/CI-артефакт/опублікований `openapi.yml`), як прив'язується версія.
3. (Опційно) у `claude-django` додати короткий розділ у `README.md` з посиланням на frontend-шаблон як офіційного споживача контракту.
