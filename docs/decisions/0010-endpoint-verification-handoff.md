# 10. Verification handoff: авто-генерація `docs/verify/<feature>.md` + реєстр маршрутів

- **Status:** Accepted
- **Date:** 2026-06-01
- **Deciders:** Project maintainer
- **Tags:** verification, docs, pipeline, api, memory, commands

## Контекст

Фіча проходить pipeline і завершується зеленими pytest-тестами всередині контейнера. Але користувач (maintainer) хоче окремий, **людино-читабельний** артефакт: «відкрий цей URL у Swagger / встав цю `curl`-команду / очікуй цей статус» — щоб швидко перевірити ендпоінти руками, не покладаючись лише на CI. Раніше такого артефакту не було: верифікація існувала тільки як автоматизовані тести.

Додатково: маршрути в різних проєктах організовані по-різному (різні префікси, вкладеність, версії), тож інструкцію перевірки не можна захардкодити — її треба **деривувати з реального контракту**, інакше вона дрейфуватиме від коду.

Також виникла потреба у швидких командах для перевірки саме **Claude-конфігу** (`.claude/settings.json`, `.mcp.json`, плагіни), не ганяючи повний чотирископовий `/doctor`.

## Рішення

Вводиться **verification handoff** — обов'язковий, авто-генерований наприкінці feature-pipeline (це «Варіант 1» — автоматичний блок), плюс окрема команда `/verify` для on-demand.

1. **Правило `.claude/rules/verification.md`.** Кожна фіча, що додає/змінює ендпоінт, отримує `docs/verify/<feature>.md`: Swagger-кроки + готові `curl`/`httpie` з тілами й очікуваними кодами (включно з негативними 401/403/400/404/409 — лише тими, що оголошує контракт). Файл генерує `docs-writer` у фазі 6, **до** відкриття PR.

2. **Пам'ять маршрутів `.claude/memory/endpoints.json`.** Машинно-читабельний реєстр (`{method, path, app, feature, auth, statuses[], notes}`). `api-architect` записує запис у момент фіксації контракту (фаза 2) — контракт неповний, поки маршрут не записано. Реєстр живить `/verify` і авто-блок.

3. **Тристороння звірка** (як у `app-readme.md`): `endpoints.json ↔ docs/api/openapi.yml ↔ docs/api/INDEX.md`. `openapi.yml` (re-derived з коду) — джерело правди; розбіжності виправляються до схеми. Цим маршрути «перевіряються й записуються» автоматично, як просив maintainer.

4. **Команда `/verify [feature] [--run]`.** Без прапорця — регенерує `docs/verify/<feature>.md` із реєстру + схеми. З `--run` — піднімає dev-стек і ганяє `curl` проти живого сервера, звітує pass/fail (з обережністю щодо мутацій стану; ніколи не проти staging/prod).

5. **Команди `/config` і `/plugins`** — **тонкі обгортки** над `claude`-scope наявного `/doctor` (єдине джерело правди, без дублювання логіки). `/plugins` додатково друкує paste-ready блок встановлення плагінів зі Step 6 `/bootstrap`.

6. **Шаблони + bootstrap.** `templates/endpoints.json` (порожній реєстр) і `templates/verify_TEMPLATE.md` копіюються в нові проєкти; `/bootstrap` створює `docs/verify/` і кладе seed у `.claude/memory/`. Mode B має probe на наявність цих файлів.

## Наслідки

**Плюси.** Тільки-но фіча зелена — користувач має конкретний, контракт-деривований чеклист перевірки, який неможливо «вигадати» повз схему. Маршрути стають машинно-перевірюваними (`endpoints.json`), що підсилює наявну дисципліну OpenAPI-drift і per-app README. `/config` та `/plugins` дають швидкий зворотний зв'язок без повного аудиту.

**Мінуси.** Ще один артефакт на фічу (`docs/verify/<feature>.md`) і ще один файл пам'яті (`endpoints.json`) для підтримки в синхроні — пом'якшується тим, що обидва деривуються з `openapi.yml` і звіряються автоматично. `/verify --run` потребує піднятого стеку й може писати реальні рядки в dev-БД — це задокументовано в команді.

**Відкинуті альтернативи.**
- *Лише інлайн-блок у чаті, без файлу* — відхилено: не зберігається між сесіями, не потрапляє в PR/review.
- *`/verify` лише генерує, без `--run`* — відхилено: maintainer обрав обидва режими (прапорець).
- *Без окремого `endpoints.json`, лише `INDEX.md`* — відхилено: потрібне машинно-читабельне джерело для `/verify` і строгої звірки.
- *`/config` і `/plugins` як повноцінні незалежні команди* — відхилено: дублювали б логіку `/doctor`; обрано тонкі обгортки (єдине джерело правди).
