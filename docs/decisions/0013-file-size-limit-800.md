# 13. Ліміт 800 рядків на файл + CI-гейт + агент code-structure-auditor

- **Status:** Accepted
- **Date:** 2026-06-02
- **Deciders:** Project maintainer
- **Tags:** code-style, ci-gate, refactoring, agents, maintainability

## Контекст

Великі файли — типове джерело технічного боргу: один модуль на кілька сотень рядків зазвичай несе кілька відповідальностей, важче читається й рев'юиться. Шаблон уже має `code-style.md` (ruff, докстрінги) та CI-гейти (`check_stubs.sh`, `check_openapi_drift.sh`, `check_app_readmes.sh`), але не обмежував розмір файлів. Maintainer попросив, щоб агенти під час написання коду тримали **максимум 800 рядків на файл**, а більші — розбивали на менші файли, згруповані в папки, і щоб був **окремий агент**, який робить такий аудит.

## Рішення

1. **Ліміт 800 рядків** на будь-який source-файл (`code-style.md`, секція «File size limit»). Рахуються **всі рядки** (`wc -l`: код, коментарі, порожні). **Звільнено лише автогенеровані міграції** (`backend/apps/**/migrations/`); тести під лімітом нарівні з продакшн-кодом (рішення maintainer'а — опитування).

2. **CI-гейт** `scripts/check_file_size.sh` (шаблон `templates/scripts/`) — жорстко падає на будь-якому non-migration `*.py` понад `MAX_LINES` (за замовчуванням 800). Підключений у `templates/.github/workflows/backend-ci.yml` (path-тригери + крок) поряд з іншими гейтами.

3. **Спосіб розбиття — групування в пакет (папку), а не довільні розрізи:** `views.py` → `views/{invoices,payments,refunds}.py` з реекспортом публічних імен у `__init__.py`, щоб **публічний import-шлях лишався стабільним**. Розбивати по доменних швах (один ресурс / одна відповідальність на файл).

4. **Окремий агент** `code-structure-auditor` (sonnet, read-only) — міряє всі файли, класифікує (🔴 >800 / 🟡 600–800 / 🟢 <600) і для кожного 🔴/🟡 пропонує **конкретний** розклад розбиття на основі реального вмісту файлу. Сам не редагує — план віддає `django-refactoring-expert`, який виконує розбиття під зеленими тестами.

5. **Команда** `/structure-audit [path]` — запускає гейт + диспетчить аудитора. `reviewer` додатково позначає 🟡-файли (600–800) на Quality Gate.

## Наслідки

**Плюси.** Файли лишаються малими й одновідповідальними; розростання ловиться автоматично, ще до того як стане боляче. Розбиття через `__init__.py`-реекспорти не ламає виклики/роутери. Аудитор дає не «файл завеликий», а готовий план розкладки.

**Мінуси.** Поріг 800 — евристика; зрідка згуртований модуль може законно перевищувати (тоді — свідомий рефактор у пакет, не виняток у гейті). Підрахунок «усіх рядків» карає й за довгі докстрінги/коментарі — прийнято свідомо заради простоти й однозначності `wc -l` (варіант «лише логічні рядки» відхилено як складніший і менш передбачуваний).

**Відкинуті альтернативи.**
- *Тільки агент-аудитор, без CI-гейту* — відхилено: без гейту правило забувається (як показав досвід `no-stubs`).
- *Рахувати лише логічні рядки коду; звільняти тести* — відхилено maintainer'ом: усі рядки, виняток лише міграції — простіше й суворіше.
- *М'який поріг (warn 600 / fail 800)* — відхилено на користь єдиного жорсткого порога 800 (простіше; «наближення» все одно позначає `reviewer`/аудитор).
- *Робити розбиття в самому аудиторі* — відхилено: аудит має лишатися read-only; зміни коду — лише під зеленими тестами через `django-refactoring-expert`.

- `templates/.github/workflows/backend-ci.yml` — path-тригери + крок «File-size gate».
- `.claude/agents/code-structure-auditor.md` — новий агент.

- `CLAUDE.md`, `README.md`, `templates/PROJECT_README.md` — реєстрація агента/команди/гейту.
